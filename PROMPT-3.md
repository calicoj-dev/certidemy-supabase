## 2 — The leak gate, before anything is written

`scan-iso-leaks.mjs` uses 5-gram seeds with a 10-word threshold. AIMS-F's descriptions will be
one-line, in ISMS-F's house style — *"a measure that modifies risk"* is six words. **A 10-word
threshold cannot see a 9-word description.** All four ISO corpora currently stand at 0 refused,
and that number would stay at 0 whatever gets written, which is the failure mode this whole
session has been about: an instrument reporting success while not looking.

These descriptions are served over MCP at contractVersion 2 to unauthenticated callers. They
are the most exposed text in the system.

Propose an instrument that can see a one-line description, measure it, and report before you
rely on it:

- what threshold or method you propose and why
- its firing count on the existing corpus — the 1,437 rows already scanned
- its false-positive rate against text you know is original, and its true-positive rate against
  text you know is ISO's, constructed as a control set
- what it costs to run

Do not write 154 descriptions behind a gate whose sensitivity nobody has measured. If the honest
answer is that no n-gram method works at this length, say that and propose something else.

## 7 — One rule to record

**Rule — an instrument must be sensitive at the scale of what it guards.** The ISO leak scanner
uses a 10-word threshold and would have reported 0 refused across 154 one-line descriptions
regardless of what they contained, on the most exposed text in the system. A gate calibrated for
lesson bodies is not a gate for concept descriptions; it is a gate-shaped object in the right
position. Mechanism: a check states the input scale it was calibrated for, and applying it to a
different scale requires re-measuring its true-positive rate at that scale.
