## 1. THE CONFORMANCE BLOCKER IS CLOSED — dual proof

`proof` is now an array of two: `eddsa-jcs-2022` first, then `eddsa-rdfc-2022`.

1EdTech's conformance guide accepts only `eddsa-rdfc-2022` or `ecdsa-sd-2023` for
a Linked Data Proof. `eddsa-jcs-2022` is a conformant W3C cryptosuite producing
genuinely verifiable credentials — it is simply not on their list, and a verifier
implementing only RDFC could not check a Certidemy credential at all.

### 1.1 Everything was measured before anything was written

| | |
|---|---|
| canonize the credential | **37.6 ms**, 79,248 bytes of N-Quads |
| canonize the proof config | 547 bytes, **5 triples**, safe mode PASS |
| contexts to bundle | 17.5 KB, two documents |
| network calls at signing | **zero** — the loader throws on any attempt |
| import form | `https://esm.sh/jsonld@8.3.2?bundle-deps` |

`ob3.ts`'s stated reason for choosing JCS — *"requiring a JSON-LD processor plus
every referenced @context fetched and cached at signing time"* — was correct when
written and is now a **solved problem**. That comment should be updated.

The proof config was checked **property by property**, because a config
canonicalizing to fewer triples than it has properties yields a signature
covering less than it appears to — a valid-looking proof protecting nothing. All
five survive.

### 1.2 A proof set, not a replacement

VCDM 2.0 permits `proof` as an array. JCS stays and is **first**:

- the badge panel verifies it in a browser with no dependency
- anything that can sort keys and check Ed25519 can verify it
- **if the RDFC path is ever wrong, the credential remains verifiable**
- some consumers read `proof[0]` blindly

### 1.3 Two things that look cosmetic and are not

**`?bundle-deps`.** A plain esm.sh import of `jsonld` pulls
`rdf-canonize-native`, which tries to load a `.node` addon that cannot exist in an
edge runtime and fails with *"Cannot set properties of null (setting 'path')"*.

**`safe: true` on canonize.** Without it a term not defined by any context is
silently dropped and the signature covers a document missing a field nobody
noticed — this codebase's recurring failure shape, cryptographically blessed.

### 1.4 Contexts are bundled and FROZEN

`_shared/ld-contexts.data.ts`, generated by `gen-ld-contexts.mjs`, 18,294 bytes.
The loader **throws** on any unbundled URL rather than falling back to the network.

A context defines what every term MEANS. Changing one changes the RDF, the
canonical N-Quads, and every signature computed against it. **After regenerating,
run `verify-rdfc-proof.mjs` against an existing credential.** A new context
*version* is a new constant, not an edit.

### 1.5 Verified by code sharing nothing with the signer

`scripts/verify-rdfc-proof.mjs` re-derives base58, canonicalization and payload
assembly from the spec, and **fetches the public key over the network** from the
issuer document.

Run **before** deploy as a control: JCS passed, RDFC correctly reported missing.
After deploy, with `--tamper`: both verify, and **both reject a document with one
character changed.**

The tamper half is the half that matters. A proof surviving a one-character change
is not covering the document — exactly what a canonicalizer silently dropping
fields produces.

### 1.6 It broke the badge panel, and nothing caught that

`credential-data-panel.tsx` destructured `credential.proof` as an object. With a
proof set, `proofValue` and `verificationMethod` were both `undefined` and the six
checks failed **on a live credential**. Fixed with `pickProof()`.

A grep afterwards found the panel was the **only** consumer of `.proof`. That grep
took four seconds and ran after the deploy.

> **CHECKLIST: before deploying a change to the credential document shape, grep
> both repos for readers of the field you changed.** Now `CERT-PUBLISH-CHECKLIST`
> §6.5.

### 1.7 `ecdsa-sd-2023` — considered, not needed

The two cryptosuites are **alternatives**; 1EdTech accepts either. `ecdsa-sd-2023`
adds selective disclosure — a holder could present "I hold SM-AI-I" while
withholding their name. Real, and not next: it needs ECDSA P-256 (a second key
pair on a different curve) and **wallet software the holder uses to derive the
disclosure**, which this market does not have. The viewer-aware two-document split
already gives a crude version that works with every verifier today.

## 2. BAKED BADGES

`?doc=baked&code=<CODE>` returns the badge PNG with the signed credential embedded
in an `iTXt` chunk, keyword `openbadgecredential`, per OB 3.0 §10. Embedded proof,
so the chunk carries JSON, not a JWS. Compression forbidden by the spec.

A single 66 KB image that any OB3-aware system opens to find the issuer, the key,
the signature, the revocation status and **53 aligned competencies** — without
contacting us and without trusting us. ~21 KB artwork, ~45 KB credential: mostly
metadata, the inverse of what most issuers produce.

**One branch, not two.** `doc === "credential" || doc === "baked"` shares the
specimen refusal, the bearer-token viewer check, and the cache split. That last
one is why: a CDN storing a holder's baked badge and serving it to the next
anonymous visitor is exactly the disclosure the viewer-aware split prevents — now
inside a file people pass around.

**Not gated.** The holder gets a badge with their identifier; anyone else gets one
without it. Both verify. A recruiter downloading a portable proof is the feature.

**Three routes:** the function, `credentials.certidemy.com/credentials/<CODE>/badge`
(machine-facing, always public copy — that host never forwards Authorization), and
`certidemy.com/credentials/<CODE>/badge` (session-aware, so a holder's badge
carries the salted hash an HR system can match to an employee record).

### 2.1 The disclosure

Always: *"An image you can post anywhere. The full signed credential travels inside
the file."*

**Holder only:** *"This copy includes your hashed email so a receiving system can
match it to you. The hash can't be reversed, but anyone who already knows your
address could confirm it from this file."*

`ob3.ts` states it exactly: **extraction is infeasible, confirmation is not.** They
should know before they post, not after.

**KNOWN GAP:** the `.jsonld` download in `credential-data-panel` has identical
exposure and says nothing.

## 3. THE SAME BUG, TWICE

Both proxies read the upstream body with `.text()`, which decodes as UTF-8. Every
invalid byte becomes U+FFFD, so a baked PNG came back **corrupt with a 200**:

```
expected   65,804 bytes
received   84,276 bytes
iTXt length reading 3,186,606,013
```

Found in the Worker, fixed, then found again an hour later in
`certidemy-web/lib/openbadge/proxy.ts` — and only because a byte count was
compared against a known-good number. **The extractor still printed plausible
JSON**, because the credential payload is ASCII-safe.

> **`arrayBuffer()` is correct for text and binary alike. There is no reason to
> use `.text()` in a pass-through proxy, ever.**

## 4. THE ANCHOR SPINE

### 4.1 What it actually is, stated plainly

This is the part that sounds bigger than it is until you understand it, and then
it is genuinely useful precisely *because* you understand it.

**A hash of each credential document goes into a Merkle tree. Only the tree's root
is published. That root is a 64-character number that means nothing to anyone
looking at it.**

What it proves: *this exact document existed by this date.* Byte for byte. Change
one character and the hash is unrecognisable.

What it does **not** do, and these matter:

- **No credential data goes anywhere.** Not the holder's name, not the 53
  alignments, not the identifier hash. Nothing personal reaches a public ledger.
- **It is not storage and not a backup.** Proving anything requires still holding
  the document and re-hashing it. Lose the document and the number proves nothing.
- **It does not prove authorship.** The Ed25519 signature does that. The anchor
  adds an independent *date*.

### 4.2 Why it is worth having anyway

Not because the technology is impressive — because **the claim is cheap, true, and
checkable**, and because "blockchain" appears in RFP checkboxes written by people
who could not define it.

The position it buys is not *"we're a blockchain platform."* It is: **nobody can
say Certidemy hasn't got that covered**, and when someone asks, the answer is
precise rather than evasive. Knowing exactly what it does is what makes it
defensible.

The Class A sentence, once upgrade completes:

> Every credential is hashed at issue into a Merkle tree, and the root is
> timestamped to Bitcoin. Anyone can prove the document existed on its issue date
> without trusting us.

**Class C, forbidden:** "blockchain-verified", "blockchain-based". The credential
is verified by a **signature**. The anchor adds a date. Saying otherwise is the
technically-adjacent overclaim CLAIMS-POLICY exists to catch.

### 4.3 Migration 227 — the spine

`credential_anchors` (root, leaf_count, doc_version, built_at, chain, txid,
anchored_at) plus `anchor_id` / `anchor_leaf` / `anchor_path` on `credentials`.

**Chain-agnostic by design.** The tree was built and useful before any chain
existed: the leaf alone proves a credential has not changed since it was hashed.

**ONE TREE ACROSS ALL ISSUERS**, unlike status lists. A status list is a *signed
document asserting an issuer's revocations*, so it must be per-issuer. A Merkle
leaf asserts nothing and is signed by nobody — a shared tree leaks nothing and
stays one submission per day however many partners exist.

**`doc_version` is load-bearing.** `open-badge` rebuilds and re-signs on every
fetch, so a leaf is only meaningful against a known emitted shape. Adding
`eddsa-rdfc-2022` changed every credential; anchors built the day before would
have silently stopped matching.

### 4.4 The hash convention, stated because it must be reproducible

```
leaf      = sha256( utf8 bytes of the credential document AS SERVED )
internal  = sha256( left32 || right32 )   raw bytes, not hex strings
odd node  = PROMOTED unchanged, never duplicated
ordering  = leaves sorted by credential_code, ascending
stamped   = the RAW 32 BYTES of the root, not its hex string
```

Promotion rather than duplication avoids the **CVE-2012-2459** ambiguity where two
different leaf sets produce the same root.

The builder **fetches each credential anonymously and hashes what is actually
served** — not a document assembled locally. It aborts if an anonymous fetch
returns `identifier[]`, which would be a disclosure bug worth stopping on.

### 4.5 The proof endpoint

`?doc=anchor&code=<CODE>` returns leaf, path, root, docVersion, chain, txid and
the algorithm description.

**The proof cannot live inside the credential.** The leaf is a hash *of* the
credential; embedding the result changes the document and invalidates it. Hence a
separate endpoint.

**Tiny by construction:** one sibling per level. Two credentials → one sibling. A
million → twenty. A verifier never sees any other credential, and every sibling is
an opaque 32 bytes.

**Not signed, deliberately.** A signature would prove Certidemy asserts the proof,
which is worth nothing — it either recomputes the root or it does not.

`check-anchor-proof.mjs` verifies independently: fetch both public URLs, hash,
climb, compare. **`ROOT MATCH: true` on both live credentials.**

### 4.6 Migration 228 — OpenTimestamps

**There is no txid.** You never send a transaction. Four calendar servers aggregate
submissions from everyone into their own tree, commit one root to Bitcoin, and pay
the fee. The `.ots` proof file **is** the receipt.

**Two states, and the schema tells them apart:**

```
ots_proof set, ots_upgraded_at NULL   submitted, no Bitcoin timestamp yet
ots_proof set, ots_upgraded_at set    confirmed, anchored_at is real
```

`anchored_at` stays NULL through the pending phase and is set from the **Bitcoin
block time**, never our clock. A UI reading the first state as "anchored" would
claim a timestamp that does not exist.

**First run:** two roots, four calendars each (alice, bob, finney, catallaxy),
700–950 byte proofs, all pending. Four calendars is redundancy — each carries an
independent path to a block.

### 4.7 The dependency fight, and why it ended where it did

This took three attempts and the reasoning is worth keeping.

**`javascript-opentimestamps`** — deprecated alias, **6 critical**, and npm
*skipped integrity verification on a git dependency* in a package whose job is
cryptographic proof.

**`opentimestamps`** (current name) — 2 critical: `request@2.88.2` (unpatchable
SSRF, dead since 2020) and `form-data`.

**Python `opentimestamps-client`** — the reference implementation, and it **will
not run on Windows**: `python-bitcoinlib` probes for `libeay32`, an OpenSSL 1.0 DLL
that stopped existing in 2018.

**Both reference clients are visibly unmaintained.** That is a fact about the
ecosystem worth knowing before depending on it.

**What resolved it:** a `form-data` override cleared **both criticals**. What
remains is moderate, and it lives in `scripts/anchor/` with its own
`package.json` — so the main tree stays at **zero vulnerabilities** and nothing
else can import it.

The residual SSRF: a malicious calendar redirects the script to an internal
address. On a **GitHub Actions runner** — disposable Ubuntu, no internal endpoints,
destroyed after the job — there is nowhere for it to go. SSRF makes requests; it
does not read environment variables.

### 4.8 `this`-binding, the bug that named the wrong thing

```
const { stamp } = pkg;  await stamp(d);
-> Cannot read properties of undefined (reading 'makeMerkleTree')
```

`stamp()` reaches for `makeMerkleTree` through `this`. Destructured, the receiver
is `undefined`. **The error names a missing function; the problem is a missing
receiver.** Classes may be destructured; module functions must be called as
`ots.stamp(...)`.

## 5. RULES EARNED

**A script whose job is verification reported success on nothing.** The anchor
builder printed `merkle root: undefined`, `leaves: 0`, `self-check: all 0
inclusion proof(s) recompute the root` — because an edit replaced `process.exit(0)`
with `process.exitCode`, which does not stop execution. Everything now lives in
`main()` and returns; the self-check aborts on a zero leaf count.

> **Six instances this session of an operation reporting success on nothing.** The
> mint writing no row, `credential-og` 401 to crawlers, `.text()` corruption twice,
> the anchor builder's empty self-check, an extractor printing plausible JSON from
> a corrupt file. **Every one was caught by asserting a specific expected value** —
> 65,804 bytes, `iTXt`, exactly one keyword, exit code 0 — and none would have been
> caught by "did it respond".

**`autoRefreshToken: false` on any service-role Supabase client in a script.** The
refresh timer keeps the loop alive and `process.exit()` aborts Node on Windows with
a libuv assertion after printing the right answer.

**`deno check` needs `--node-modules-dir=auto` in the supabase repo.** `npm install`
created a `node_modules` that puts Deno in manual mode; the failure reads like a
code error.

**Every inline PowerShell here-string patch introduces bare LF into a CRLF file.**
Bitten twice. The three bare-LF lines in `open-badge/index.ts` came from
`patch-baked-cast.mjs`. **Downloaded `.mjs` files do not have this problem** — one
more reason for the file-delivery workflow.

**Do not print a runnable command and then say "don't run this".** I did, it ran,
and it committed a broken script. If it should not be run, it should not be
printed.
