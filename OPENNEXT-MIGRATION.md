## 1. The open question, answered: it is a migration

`HANDOFF-v9_0.md` §7 item 1 said the `_headers` question *"decides whether §5 is
a migration or a redesign."*

**It is a migration.**

### `public/_headers` is honoured, and the adapter's own instructions rely on it

`@opennextjs/cloudflare` supports it, and not incidentally: **it is in the
adapter's own get-started instructions.** Cloudflare Static Assets default to
`max-age=0, must-revalidate`, and matching Next's immutable-asset behaviour for
`/_next/static/*` is done **through that file**. An adapter whose setup
documentation tells you to write a `_headers` file is not one that ignores it.

### The real constraint is narrower than "does it work"

**Headers declared in `_headers` are NOT applied to responses generated by
Worker code.** They apply to static assets.

So the question is not *"is the file read"* — it is *"is every rule in it
pointed at a static asset, or is one of them pointed at a route?"* A rule
matching a Worker-generated path would go silent, and silently: the response
still returns, without the header.

### All five rules are class (a), and that was resolved by listing

Every rule matches **real files under `public/`**, established by listing the
directory rather than by reasoning about the paths:

- 9 brand PNGs
- 12 badge PNGs
- 4 og PNGs
- `apple-touch-icon.png`
- the Next build output (`/_next/static/*`)

**No route under `app/` emits any matched path.** There is no `ImageResponse`
and no `next/og` anywhere in the repository — so there is no generated image
route that could collide with the image paths these rules cover.

**Nothing goes silent.** Conditional on `assets.run_worker_first: false`, which
step 1.4 sets.

### The near-miss, recorded because the next reader will trip on it

**`app/credentials/[code]/badge/route.ts` has "badge" in its name.** It serves
`/credentials/<CODE>/badge` — a Worker-generated response.

**It is matched by no rule.** The badge rule covers `/badges/*` under `public/`;
this route is under `/credentials/`. The two are unrelated and the collision is
in the word, not the path.

Written down because "badge" appearing in both a `_headers` rule and a route
filename is exactly the coincidence someone re-checking this will find, and it
looks like the counter-example that breaks the conclusion. It is not.

### CONFIRMED TWICE IN EXECUTION, and neither confirmation is documentation

**The conclusion above no longer rests on the adapter's documentation at any
point.** Two independent measurements at Phase 1:

**wrangler printed `Parsed 5 valid header rules` at preview startup,
unprompted.** Not asked for, not a flag — the adapter reporting the same count
this section derived by listing. Five rules written, five rules parsed.

**Step 1.6 hashed all 30 files under `public/` against `.open-next/assets`:**

```
30 present, 0 missing, 0 byte-different
_headers byte-identical at e7931a71e6ab00d9
```

**With a hash control**, so the comparison was shown capable of reporting a
difference rather than merely reporting none.

The first confirms the file is read and understood. The second confirms every
asset the rules point at actually ships. **Together they close the one gap this
section originally had** — see §4 step 1.6, which existed for exactly that
reason.

## 3. The sequencing constraint: the split is impossible

The obvious plan — *upgrade Next first, separately, so the attribution is not
lost* — **is not available at any price.**

### The peer ranges do not intersect

```
next-on-pages          next >=14.3.0 <=15.5.2
@opennextjs/cloudflare  next >=15.5.24 <16 || >=16.3.3
intersects              false
```

**The gap is exactly 15.5.3 through 15.5.23** — versions neither adapter
accepts. There is no Next version that satisfies both, so there is no
intermediate state in which one change has landed and the other has not.

**Any Next ≥ 15.5.24 fails `npm` clean-install while `next-on-pages` is still a
dependency** — the identical `ERESOLVE` that already failed CI.

**So the adapter swap and the Next upgrade land in ONE commit.** See §6 for what
that costs and how it is paid.

### 15.5.24 is not a conservative pick among candidates

It is the only pick.

**It is simultaneously the floor of OpenNext's range and the head of the
published 15 line** — npm's `backport` dist-tag points at it. There is no
"slightly newer 15" to prefer and no "slightly older 15" that OpenNext accepts.

**Pin exact. No caret.**

### Next 16.3.3 is forbidden

OpenNext's peer range has a second branch, `>=16.3.3`. **Do not take it.**

`next-intl@3.26.5` peers `next: ^15.0.0`. Next 16 is outside it. The Next 16
door stays closed until `next-intl` is upgraded, **which is its own change with
its own i18n review surface across three locales.**

- **and the negative half**: the **seven convention files still unpinned**, and

## 5. What could make this plan wrong

### #1 — The two adapters' peer ranges do not intersect, so "upgrade Next first, separately" is impossible

```
next-on-pages : >=14.3.0 <=15.5.2
opennext      : >=15.5.24 <16 || >=16.3.3
intersects    : false
```

There is no Next version that satisfies both. The gap is exactly
15.5.3 … 15.5.23 — versions neither adapter accepts.

This kills the sequencing decided earlier in this work (*"upgrade Next first and
separately so attribution isn't lost"*). Any Next ≥ 15.5.24 fails npm
clean-install while `next-on-pages` is a dependency — the identical `ERESOLVE`
that failed CI on 15.5.24 already. The Next upgrade and the adapter swap must
land in one commit, and **the attribution that separation was meant to preserve
is not available at any price.** Plan the commit message to carry what the split
would have carried.

### #2 — The jump is 15.1.4 → 15.5.24, and 15.5.2 in between is a known unexplained CI failure with no local reproduction

The last version proven to deploy here is 15.1.4. The lowest OpenNext accepts is
15.5.24. Every version between them is either unproven or actively failed.

The mitigating fact, and it is a strong one: the 15.5.2 CI refusal was
`next-on-pages`' own edge-runtime check (`/_not-found` not configured to run
with the Edge Runtime). OpenNext forbids the edge runtime entirely — there is no
such check to fail. So the specific failure is expected to evaporate rather than
be fixed.

But that is a prediction, not a measurement, and it is the plan's central bet.
If 15.5.24 fails for some other reason, you find out at step 2.2 with both
changes entangled and no way to bisect them. Phase 2 is structured so that
discovery happens on workers.dev with production untouched — that is the whole
reason the gate sits before DNS.

> **[CORRECTION — the mitigation above is DEMOTED, and must not be
> re-strengthened.]**
>
> The paragraph calling it *"a strong one"* rests on an explanation that has
> since been **retracted**. `HANDOFF-v9_0.md` §3 records it: the claim that
> *"Next 15.5.2 emits `/_not-found` as `nodejs22.x` regardless of the edge pin"*
> **does not reproduce.** Four full builds on 15.5.2 — cached, clean, Node 24,
> and Node 22.16.0 matching CI exactly — **all emit it as edge**, and route by
> route 15.1.4 and 15.5.2 differ in exactly one place: a dedup symlink.
>
> **The inference survives only as a CONDITIONAL.** *If* the refusal was
> `next-on-pages`' edge-runtime check, then OpenNext has no equivalent and it
> evaporates. **What is gone is confidence in the antecedent, not the
> implication.**
>
> **And the baseline undercuts it from a second, independent direction.**
> `next-on-pages` ships **two `nodejs22.x` functions on 15.1.4 in a build that
> deploys** — `_error.func` and `favicon.ico.rsc.func`. **Its error message
> states a rule it does not enforce.** So *"a Node function appeared where an
> edge one was required"* is not, by itself, an explanation for anything.
>
> **The consequence, which is what a reader at the gate actually needs:**
>
> **THE BET IS UNCHANGED IN SIZE, AND THE PLAN IS ALREADY STRUCTURED FOR IT.**
> Step 2.3 exists precisely because a 15.5.24 failure *for some other reason*
> would surface with three majors entangled and no way to bisect — on
> workers.dev, with production untouched.
>
> **Demoting the mitigation changes no step. It changes what someone believes
> when they read the failure.** Which matters: a reader who thinks the mechanism
> is understood will look for a variant of it, and the trigger is unknown.

### #3 — wrangler must go 3.114.17 → v4, a second unvalidated major in the same commit

## 6. The commit message must carry what the split cannot

**Because §3 makes the split impossible, the attribution it would have preserved
has nowhere else to live.**

Three changes land in one commit: **the adapter swap**, **the Next upgrade
15.1.4 → 15.5.24**, and **the wrangler major 3 → 4**. A bisect cannot separate
them, because there is no revision in which one landed without the others — the
peer ranges forbid it.

**So the Phase 1 commit message must state which change is which**: which lines
are the adapter, which are Next, which are wrangler, and what each was expected
to do.

**A future bisect will land on that commit and have to read prose, because it
cannot have commits.** Write the message for that reader.

## 7. What this cost to learn

Only the durable ones. Each was paid for.

### Local build output does not predict the deployed artifact

**Production chunks differently from local.** The four production carriers of
the Supabase credentials **are not in the local manifest's carrier list at
all.**

So a check anchored on a chunk filename — the obvious way to write it — **would
have reported a healthy build as a missing environment.** The anchor has to be
something the deploy cannot rename.

### A needle must be derived from the source of truth, never hand-copied

**A hand-truncated JWT prefix produced a FALSE ZERO on a healthy build.** The
needle was wrong, the code was right, and **the output was silent about which**
— a zero result looks identical whether nothing is there or you asked for the
wrong thing.

Derive the needle from the same file the code reads. `check-deploy.mjs` reads
its headline from `messages/<locale>.json` for exactly this reason.

### A control proves an assertion can FAIL. It does not prove it can PASS.

**The 500 shell and the 404 shell load byte-identical script sets.** So on a
broken origin, the control could not discriminate two of the five assertions —
both the real page and the bogus path produced the same evidence.

**Only a known-good carrier route closed that.** A control establishes the
negative half; a route known to carry the thing establishes the positive half.
**Both halves, or the check is only half instrumented.**

**And this lesson failed on the document that records it.** Verifying this file
for stray control bytes, `grep -c $'\0'` returned **793** — which is the line
count, because `$'\0'` collapses to an **empty pattern** in bash and matches
every line. **It would have reported the same "clean" for any file, including
one full of NULs.** The instrument answered a different question from the one
asked, and the answer was plausible enough to accept. Re-running as a byte-range
check with a **planted-NUL control** exposed it: 0 on the file, 1 on the
control. **That is the third time in this migration a control caught the
instrument rather than a defect** — the hand-truncated JWT needle, the
local-manifest chunk analysis, and this.

### An error or 404 shell loads only framework chunks — and this is the structural one

In any build, under any chunking, an error or 404 shell loads framework chunks
and nothing else.

**That is structural and survives a chunking change.** The manifest-derived
justification for the same conclusion did not — it was true of one build's
output and would have gone stale the moment the bundler moved.

**When two arguments reach the same place, keep the one that does not depend on
today's artifact.**

### A guard can be right in intent and wrong about the population

**Added by Phase 1 — this is the fifth instance of the family already recorded
above**, alongside the hand-copied needle and the control-without-a-carrier. The
1.3 line-ending abort was correct about what it wanted to prevent and wrong
about what it would encounter: four files in this repository are genuinely mixed
CRLF/LF, all four carried pins, and the abort would have stopped the edit at 77
of 81 — with the four survivors reading as a failed edit rather than a property
of the files.

**The fix was to make the abort unnecessary, not to suppress it.** A byte-level
line splice has nothing to say about line endings, so the question stops being
asked rather than being answered wrongly. Suppressing the guard and removing the
need for it look identical in the diff and are not the same act.

**Before writing a guard, measure the population it will run against.** The four
mixed files were in the repository the whole time. Nothing prevented measuring
them except assuming what they would look like — which is the same assumption
that produced the wrong pin count in v9.0, from the wrong side of `.gitignore`.

### The valuable part of a risky change often edits nothing

**Phase 1's two best measurements produced no commits.** Step 1.6's 30-file hash
and step 1.7's preview are where this plan stopped resting on documentation and
on reasoning respectively; both produced zero lines of diff. Meanwhile three of
the six commits were unplanned work.

**A plan tracked by commits would have counted this exactly backwards.**

**And 1.6 went past what the plan asked for, on purpose.** The step said "list
the output root to confirm the files are present". Hashing all 30 assets was
chosen over listing them because **presence and identity are different
properties**, and only identity supports what §1 needs — a listing cannot tell a
correct asset from a truncated one. That was not luck, and the distinction is
the transferable part: **when a step names the cheap check, ask what property
the conclusion actually requires.**
